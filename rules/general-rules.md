# General Engineering Rules

هذه القواعد فعالة لكل مهمة SDD في المستودع.

## Source of Truth

- الـspec المعتمد هو مصدر حقيقة نطاق المهمة ومعايير قبولها.
- `AGENTS.md` و`rules/project-rules.md` هما مرجع المعمارية والقيود الدائمة.
- عند تعارض الخطة مع الـspec، يتوقف التنفيذ حتى تحديثهما واعتمادهما.

## Scope and Changes

- لا توسّع نطاق المهمة بصمت، ولا تخلط إصلاحات غير مرتبطة في commit واحد.
- حافظ على تغييرات المستخدم الموجودة ولا تعدّل ملفات محلية غير داخلة في الخطة.
- فضّل أصغر تغيير يحقق معايير القبول ويحافظ على التوافق.
- لا تضف dependency إلا مع تبرير وتأثير أمني وتشغيلي مسجل في الخطة.

## Security and Privacy

- لا تُcommit مفاتيح أو tokens أو service accounts أو ملفات `.env` الحقيقية.
- لا تسجل أسرارًا أو بيانات شخصية أو محتوى فيديو حساسًا في logs.
- تحقق من المدخلات عند حدود النظام، وقيّد أسماء ومسارات الملفات.
- لا تعتمد على فحص الواجهة وحده لحماية كتابة backend أو Firestore.

## Errors and Logging

- لا تفشل بصمت؛ الأخطاء المتوقعة تُعاد برسالة مفهومة، وغير المتوقعة تسجل بسياق كافٍ دون أسرار.
- لا تستخدم catch عام إلا عند boundary واضح مع معالجة أو إعادة رفع مناسبة.
- اجعل رسائل الخطأ تتضمن العملية ومعرّف job عندما يكون آمنًا.

## Code Quality

- اتبع أسلوب اللغة والبنية الموجودة، ولا تنشئ abstraction بلا حاجة حالية.
- علّق على سبب المنطق المعقد، وليس على ما يفعله السطر حرفيًا.
- لا تترك dead code معلقًا، ولا تغيّر formatting لملفات غير مرتبطة.

## Verification

- كل bug fix يحتاج regression test عندما يكون عمليًا.
- الاختبارات يجب أن تكون deterministic؛ اعزل الخدمات الخارجية أو وثّق الاختبار اليدوي المطلوب.
- لا تُعلن المهمة مكتملة قبل تسجيل نتائج التحقق مقابل كل Acceptance Criterion.
- نجاح build وحده لا يثبت صحة تدفق المستخدم.

## Git and Review

- استخدم feature branch وPull Request؛ لا push مباشرًا إلى `main`.
- لا تضع generated runtime data أو نتائج الفيديو أو ملفات البيئة في Git.
- وصف PR يربط مهمة SDD ويذكر التحقق والمخاطر وخطوات النشر.
