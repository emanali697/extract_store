# دليل استخدام SDD

## لماذا نستخدمه؟

SDD يجعل الـspec هو مصدر الحقيقة للمهمة. لا نبدأ من تعديل عشوائي في الكود ثم نحاول تذكر المطلوب؛ نحدد النتيجة أولًا، نخطط لتأثيرها، ننفذها، ثم نسجل دليل التحقق.

## 1. Specify

اختر اسمًا قصيرًا بصيغة `kebab-case`، مثل `fix-reviewed-excel-export`، ثم أنشئ:

```text
.tasks/fix-reviewed-excel-export/spec.md
```

انسخ قالب `spec.template.md`. ابدأ بحالة `Draft` أثناء النقاش. يجب أن يجيب الملف عن:

- ما المشكلة الحالية؟
- ما السلوك المطلوب للمستخدم؟
- ما القيود، خصوصًا Firebase وبيانات التجار والأسرار؟
- كيف سنعرف أن الحل صحيح؟
- ما الحالات غير المعتادة وما الذي لن ننفذه؟

بعد موافقة صاحبة المشروع، غيّر حالة الـspec إلى `Approved`. لا يبدأ التنفيذ وهي `Draft`.

## 2. Plan

أنشئ `plan.md` من القالب، واربطه بمسار الـspec. يجب أن يحدد:

- approach واضح لا مجرد وصف الهدف؛
- أثر التعديل على frontend وbackend وFunctions والبيانات والنشر؛
- خطوات مرتبة وملفات محددة؛
- اختبارات وأوامر تحقق متناسبة مع المخاطر؛
- rollback plan ومخاطر معروفة.

يبدأ `plan.md` بحالة `Draft`، وبعد مراجعته يصبح `Approved`.

## 3. Implement

نفّذ الخطوات المعتمدة فقط. أثناء التنفيذ:

- اقرأ `AGENTS.md` و`rules/` والـspec والـplan أولًا.
- لا توسّع النطاق بصمت. إذا تغير المطلوب، حدّث الـspec والـplan واحصل على اعتماد جديد.
- لا تعدّل ملفات المستخدم المحلية أو الأسرار.
- لا تكتب إلى `traders-data-live` ما لم توجد مهمة منفصلة وموافقة صريحة مع تفعيل الحارسين frontend وbackend.
- أضف اختبار regression للـbug عندما يكون ذلك عمليًا.

## 4. Check

أنشئ `check.md` من القالب وسجل النتائج الفعلية، لا الأوامر المقترحة فقط. راجع كل Acceptance Criterion واربطه بدليل: اختبار، build، فحص يدوي، screenshot، أو سبب موثق لعدم الإمكان.

بعد نجاح التحقق:

- حالة `check.md`: `Passed`.
- حالة `spec.md` و`plan.md`: `Complete`.
- شغّل `python scripts/sdd_check.py --all`.
- أضف مسار المهمة إلى Pull Request.

إذا فشل شرط قبول، تظل المهمة غير مكتملة حتى الإصلاح أو تعديل الـspec بموافقة صريحة.

## التعامل مع Codex

يمكن طلب المراحل بصياغة طبيعية:

```text
اعمل Specify لمهمة fix-upload-progress من غير تعديل كود.
اعمل Plan للمهمة بعد ما أعتمد الـspec.
نفّذ خطة .tasks/fix-upload-progress فقط.
اعمل Check للمهمة وسجّل النتائج.
```

عند طلب تنفيذ feature أو bug fix مباشرة، على الوكيل إنشاء/تحديث مستندات SDD ضمن نفس المهمة قبل تعديل السلوك، إلا لو طلبتِ صراحة مرحلة واحدة فقط مثل Specify.

## Pull Requests

كل PR سلوكي يذكر:

- `SDD Task: .tasks/<task-name>/`
- ملخص السلوك المتغير
- أوامر التحقق ونتائجها
- أي مخاطر أو خطوات نشر

GitHub Actions يفحص بنية SDD. لجعله مانعًا للدمج، فعّلي check باسم **SDD validation** كـrequired status check في branch protection الخاصة بـ`main`.

## الاستثناء

الاستثناء مسموح فقط عندما لا يتغير runtime behavior أو API أو schema أو deployment. أضيفي في PR:

```text
SDD-Exempt: documentation typo only
```

لا ينطبق الاستثناء على bug fixes أو تغييرات الإعدادات المؤثرة أو قواعد Firebase أو تحديث dependencies المؤثر على التشغيل.
