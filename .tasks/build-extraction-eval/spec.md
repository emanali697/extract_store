# Build Extraction Evaluation Foundation

Status: Complete
Owner: Project owner
Type: Feature

## Context

دقة استخراج المتاجر مقدرة حاليًا بحوالي 36%، لكن لا توجد مجموعة مرجعية ثابتة أو أداة قياس تفصل بين:

- متجر لم يكتشف أصلًا؛
- متجر اكتشف باسم خاطئ؛
- اسم صحيح جزئيًا؛
- رقم هاتف خاطئ أو غير ظاهر في الفيديو؛
- تكرار نفس المتجر في أكثر من نتيجة؛
- مطابقة Google Places خاطئة رغم صحة الدليل البصري.

نحتاج أساس تقييم قابل لإعادة التشغيل قبل تغيير sampling أو معالجة الصور أو OCR أو Gemini، حتى نقارن كل نسخة على نفس البيانات بدل الاعتماد على الانطباع البصري.

## Current Behavior

- لا توجد مجموعة ground truth بإصدار ثابت داخل المشروع.
- لا توجد أداة تحسب precision وrecall ودقة الأسماء والهواتف ونسبة التكرار.
- ملخص الـpipeline الحالي يحسب أعداد النتائج والهواتف والمطابقات، لكنه لا يقارنها بمتاجر صحيحة موثقة يدويًا.
- مجلدات `backend/jobs/<job_id>/` تحتوي نتائج فعلية يمكن تقييمها، لكن لا يوجد عقد بيانات يربطها بتعليقات بشرية ثابتة.

## Requirements

- إضافة صيغة JSON مرجعية قابلة للمراجعة البشرية لكل فيديو تتضمن:
  - معرف العينة ومعرف الفيديو أو job دون حفظ الفيديو نفسه في Git؛
  - قائمة المتاجر الحقيقية بالترتيب على مسار الفيديو؛
  - الاسم الحرفي الصحيح وبدائل مقبولة اختيارية؛
  - الهاتف الصحيح عندما يكون ظاهرًا، مع تمييز `visible` و`not_visible` و`unreadable`؛
  - فترات أو أرقام الفريمات التي يظهر فيها المتجر عندما تكون معروفة؛
  - الإحداثيات المرجعية الاختيارية؛
  - ملاحظات جودة مثل blur والزاوية والحجب واللغة؛
  - معرف مجموعة للمتجر يسمح بقياس التكرارات.
- إضافة schema validation يمنع العينات الناقصة أو المتعارضة، خصوصًا الهاتف غير الظاهر المسجل كخطأ استخراج.
- إضافة CLI محلي يقرأ ملف ground truth وملف نتائج pipeline بصيغ v3 أو v5 أو v6.
- تنفيذ matching حتمي وقابل للمراجعة بين النتائج والمتاجر المرجعية، مع السماح بملف mapping يدوي للحالات غير الحاسمة بدل استخدام LLM داخل القياس.
- حساب المقاييس التالية منفصلة:
  - store detection precision وrecall وF1؛
  - exact-name accuracy؛
  - normalized/fuzzy-name accuracy مع إظهار threshold المستخدم؛
  - phone coverage لكل المتاجر؛
  - phone exact precision وrecall للهواتف الظاهرة القابلة للقراءة فقط؛
  - duplicate rate؛
  - false-positive counts للإعلانات والمركبات والكيانات غير التجارية عندما تكون معلّمة؛
  - دقة `auto_passed` منفصلة عن الدقة الإجمالية؛
  - coverage وعدد العينات حتى لا تعرض نسبة بلا مقام واضح.
- إخراج تقرير JSON آلي وتقرير Markdown مقروء يتضمن الأخطاء على مستوى كل متجر.
- توفير مثال صغير synthetic أو منزوع البيانات يثبت عقد الملفات وتشغيل الأداة، دون إضافة صور أو فيديوهات أو بيانات شخصية حقيقية إلى Git.
- توثيق خطوات إنشاء أول Mini Eval من 50 متجرًا ثم توسيعه إلى 200 متجر على الأقل قبل اعتماد قرارات معمارية كبيرة.
- لا تتصل أداة التقييم بخدمات خارجية ولا تكتب إلى Firebase أو Firestore أو `traders-data-live`.

## Constraints

- بيانات الفيديو واللافتات وأرقام الهواتف الحقيقية تبقى خارج Git في مسار محلي أو Cloud Storage مصرح به.
- ملفات الأسرار وservice accounts و`.env` ممنوعة من ملفات التقييم والتقارير.
- القياس يجب أن يكون deterministic؛ نفس المدخلات والإعدادات تعطي نفس النتائج.
- تطبيع العربية لا يحول التطابق التقريبي إلى تطابق حرفي؛ يتم الإبلاغ عن المقياسين منفصلين.
- الهاتف لا يدخل مقام phone recall إلا إذا كانت الحقيقة المرجعية تؤكد أنه ظاهر وقابل للقراءة.
- لا يغيّر هذا العمل pipeline الإنتاج أو API أو frontend أو منطق `auto_passed`.
- لا يغيّر fallback الحالي `v6 > v5 > v3`.

## Acceptance Criteria

- يوجد schema موثق لملف ground truth ويقبل الحالات `visible` و`not_visible` و`unreadable` للهاتف.
- يرفض validator عينة فيها هاتف مصنف `not_visible` مع قيمة هاتف صحيحة غير فارغة، ويعرض رسالة تحدد العينة والمتجر.
- يستطيع CLI تقييم ملف نتائج v3 أو v5 أو v6 مقابل ground truth دون اتصال شبكي.
- ينتج CLI ملف JSON وتقرير Markdown يحتويان جميع المقاييس المطلوبة مع numerator وdenominator.
- يميز التقرير بين exact-name وnormalized/fuzzy-name، وبين phone coverage وphone exact precision/recall.
- يقيس التكرار على مستوى المتجر المرجعي ولا يعتبر ظهور نفس المتجر في عدة فريمات عدة متاجر صحيحة.
- يسرد التقرير false positives وfalse negatives وحالات الاسم أو الهاتف غير الصحيحة بأرقام تعريف قابلة للمراجعة.
- توجد اختبارات آلية deterministic تغطي على الأقل: تطابق صحيح، متجر مفقود، نتيجة زائدة، اسم عربي مختلف بحرف، هاتف خاطئ، هاتف غير ظاهر، ونتيجة مكررة.
- توثق نتيجة تشغيل الاختبارات وPython compile و`python scripts/sdd_check.py --all` في `check.md` قبل إكمال المهمة.
- لا تتضمن تغييرات المهمة أي فيديو أو crop حقيقي أو رقم هاتف حقيقي أو secret، ولا تنفذ أي كتابة خارج ملفات التقرير المحلية.

## Edge Cases

- متجر بلا اسم عربي وله اسم إنجليزي ظاهر فقط.
- متجران متجاوران بأسماء شديدة التشابه.
- نفس السلسلة التجارية تظهر في فرعين مختلفين داخل الفيديو.
- متجر واحد له أكثر من لافتة أو أكثر من رقم هاتف.
- رقم ظاهر جزئيًا أو مختلف بين الفريمات.
- نتيجة pipeline تحمل اسم Google Places بدل النص المرئي.
- ملفات نتائج فارغة أو malformed أو تحتوي متجرًا مستبعدًا من النتائج النهائية.
- غياب GPS أو frame identifiers من نسخة قديمة من النتائج.

## Out of Scope

- تغيير frame sampling أو crop أو image enhancement.
- إضافة YOLO أو ByteTrack أو تدريب detector.
- إضافة PaddleOCR أو تغيير Cloud Vision أو Gemini.
- تغيير `auto_passed` أو review routing.
- تحسين Google Places أو GPS.
- نقل worker إلى Cloud Run Jobs.
- بناء أو وسم مجموعة البيانات الحقيقية بالكامل دون مراجعة بشرية من صاحبة المشروع.
